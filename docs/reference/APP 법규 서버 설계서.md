# APP 법규 서버 설계서

Nov 6, 2026 · @강영훈

## 1. 개요

법규 서버는 **공식 원문을 버전별로 보관하고, 조문을 구조화된 규칙(JSON)으로 바꾸고, 필지 정보를 받아 적용 규칙과 쉬운 설명을 돌려주는** 백엔드다. 웹은 이 서버의 결과만 화면에 그린다.

**MVP 범위** (기능정의서 기준): 대구 수성구 필지의 용도지역 확인, 건폐율·용적률, 검토 가능 용도, 주차 기준값(주차구획·차로 폭), 법규 근거 계층 표시, 별도 확인 항목 분리. 배치안·PDF/DXF는 이후 단계.

**설계 원칙 7가지**

1. **원문이 진실이다.** AI가 만든 값은 원문 조문에 근거 구간(span)이 있을 때만 저장한다. 근거 없는 수치는 버린다.
2. **AI는 두 번만 쓴다.** ① 오프라인에서 조문 → 규칙 JSON 추출, ② 이미 확정된 검토 결과 → 쉬운 문장 변환. 사용자 요청 시점에 AI가 법규를 새로 판단하지 않는다.
3. **사람 검수를 거친 규칙만 결과에 쓴다.** `review_status = approved`가 아닌 규칙은 "별도 확인 필요"로만 노출한다.
4. **시간을 기록한다.** 모든 법령·조례·규칙은 시행일(`effective_from/to`)과 수집일을 따로 가진다. 검토는 항상 "기준일"을 명시한다.
5. **null은 '모름'이다.** 기존 법규 정리 문서의 원칙대로 null을 규제 없음·허용·0으로 해석하지 않는다.
6. **결론 대신 상태를 준다.** 결과는 `검토 가능 / 조건부 검토 / 별도 확인 필요` 세 상태와 근거로 돌려주고, 허가 가능 여부를 단정하지 않는다.
7. **검증을 통과한 문장만 화면에 나간다.** AI가 쓴 모든 문장은 사후 검증기(9장)에서 날조·세부 왜곡·누락을 검사받고, 통과하지 못하면 원문 인용으로 대체한다.

## 2. 전체 아키텍처

서버는 오프라인 배치(원문 → 규칙)와 **사용자 요청(필지 → 결과)** 두 흐름으로 나뉘고, 둘은 규칙 DB 하나로만 만난다.

&#91;embedded content: 법규 서버 구성 · 오프라인 배치 7단계, 요청 처리 6단계\]

AI는 위쪽의 규칙 추출과 아래쪽의 쉬운 설명 두 곳에만 있고, 둘 다 뒤에 검증 단계가 붙는다. 사용자 요청 처리 중에 AI가 법규를 새로 판단하는 경로는 없다.

**기술 스택 제안**: Python(FastAPI) + PostgreSQL/PostGIS, 배치는 스케줄러(cron 또는 Celery beat), 원문은 S3 호환 객체 저장소, 웹은 Next.js + 지도 SDK(브이월드 또는 카카오맵).

## 3. 법규 계층 모델

요청하신 **국가법 → 토지법 → 지역 법규** 순서를 4개 레이어로 고정하고, 모든 문서·규칙은 반드시 하나의 레이어에 속한다. 검토 엔진은 L1부터 내려가며 값을 좁히고, L4는 마지막에 겹쳐 덮는다.

| 레이어 | 이름 | 담는 것 | 대표 자료 | 엔진에서의 역할 |
| --- | --- | --- | --- | --- |
| L1 | 국가 법령 | 법률·시행령·시행규칙·별표 | 국토계획법, 건축법, 주차장법 및 각 시행령 | 상한·하한 범위, 용도 허용 목록, 주차 기준 원칙 |
| L2 | 토지이용 규제 | 필지에 지정된 용도지역·지구·구역, 지목 | 토지이용규제기본법 체계, 토지이용계획 정보 | 어떤 L1·L3 규칙이 이 필지에 걸리는지 결정하는 '키' |
| L3 | 지역 법규 | 광역·기초 조례·규칙 | 대구광역시 도시계획 조례, 대구광역시 건축 조례, 수성구 주차장 조례 | L1 범위 안에서 지역의 실제 적용값 |
| L4 | 특화구역 중첩 | 지정 고시·계획·도면 | 지구단위계획, 연구개발특구, 경제자유구역, 문화유산 보호구역 | 해당 필지가 경계 안이면 우선 적용하거나 "별도 확인"으로 격상 |

**계층 간 연결은 '위임 관계(delegation)'로 저장한다.** 예를 들어 "국토계획법 제77조(건폐율) → 시행령 제84조 → 대구광역시 도시계획 조례 해당 조문"처럼, 하위 규정이 어느 상위 조문의 위임을 받았는지를 `delegation` 테이블에 엣지로 둔다. 결과 화면의 "상위 법령 → 시행령 → 조례" 근거 트리는 이 엣지를 그대로 따라 그린다.

**값 결정 규칙**

- L3 값이 있고 L1 범위 안이면 → L3 값 채택, 근거는 L3 + L1 함께 표시
- L3 값이 없으면 → L1 범위를 그대로 보여주고 상태는 `조건부 검토`
- L3 값이 L1 범위를 벗어나면 → 값을 쓰지 않고 `별도 확인 필요` + 검수 알림 (데이터 오류 가능성)
- L4 중첩이 확인되면 → 해당 항목을 `별도 확인 필요`로 격상하고 고시 링크 표시 (MVP에서는 지구단위계획 내용을 자동 반영하지 않음)

위 조문 번호는 연결 구조를 설명하는 예시다. 실제 데이터에는 검토 기준일의 조문을 원문에서 확인해 넣어야 한다.

## 4. 데이터 출처와 수집 방식

법규 원문은 **국가법령정보 공동활용 Open API 하나로 L1·L3를 모두 받고**, 필지·L2 정보는 주소 API와 공간정보 API로 받는다. L4 고시는 MVP에서 수작업 등록한다.

| 대상 | 출처 | 수집 방식 | 주기 | 저장 위치 |
| --- | --- | --- | --- | --- |
| L1 법률·시행령·시행규칙 | [국가법령정보 공동활용](https://open.law.go.kr/LSO/main.do) (`lawSearch.do`, `lawService.do`, 법령·시행일법령·별표 대상) | 법령ID·MST 단위 조회 → XML 원문 저장 | 매일 개정 여부 확인 | `source_document`, `document_version` |
| L3 자치법규 | 같은 Open API의 자치법규 대상 (대구광역시, 수성구) | 자치법규ID 단위 조회 | 매일 | 동일 |
| 법령 체계·위임 | 국가법령정보센터 법령체계도, 원문의 "\~조례로 정한다" 문구 | 체계도 조회 + 위임 문구 추출(AI 보조) | 개정 시 | `delegation` |
| 주소 → 지번 | [도로명주소 검색 API](https://business.juso.go.kr) | 실시간 호출, 법정동코드·지번으로 PNU(19자리) 생성 | 요청 시 | `parcel_cache` |
| 필지 경계·지목·면적 | 브이월드 연속지적도·토지임야정보 API | 실시간 호출 후 캐시 | 요청 시, 캐시 30일 | `parcel`, `parcel_geometry` |
| L2 용도지역·지구·구역 | 브이월드 토지이용계획 속성 API (토지이음과 같은 원천) | PNU로 조회 | 요청 시, 캐시 30일 | `parcel_designation` |
| 건축물 현황 (선택) | 공공데이터포털 건축HUB 건축물대장 API | PNU로 조회 | 요청 시 | `parcel_building` |
| L4 지정 고시 | [토지이음 고시정보](https://www.eum.go.kr/web/am/amMain.jsp) | MVP는 관리자 화면에서 수작업 등록(고시번호·일자·도면 링크) | 월 1회 점검 | `source_document(layer=L4)` |

**수집 원칙**

- 원문은 받은 그대로(XML/HTML/PDF) 객체 저장소에 두고 `sha256`으로 변경을 감지한다. 해시가 바뀌면 새 `document_version`을 만들고 그 버전의 규칙은 다시 추출·검수 대기로 돌린다.
- 시행일이 미래인 버전(예: 기준일 이후 시행되는 대구광역시 건축 조례 개정분)은 저장하되 `effective_from`으로 걸러 검토에 쓰지 않는다.
- 브이월드·도로명주소 API는 인증키와 호출 한도가 있으므로 서버에서만 호출하고 키를 브라우저에 노출하지 않는다.
- Open API의 대상(target) 이름과 응답 필드는 구현 전 공식 가이드에서 다시 확인한다. 이 표는 출처 구성을 정한 것이지 호출 규격을 검증한 것이 아니다.

## 5. DB 스키마 개요

DB는 **PostgreSQL + PostGIS** 한 곳에 22개 테이블과 조회 함수 1개, 뷰 1개를 8개 묶음으로 둔다. 전체 DDL은 함께 전달한 `schema.sql`에 있고, PostgreSQL 16에서 로드 테스트를 통과했다(PostGIS 공간 컬럼은 테스트 환경에서 제외).

| 묶음 | 테이블 | 핵심 역할 |
| --- | --- | --- |
| A. 관할 | `jurisdiction` | 법정동코드 기준 전국 → 시·도 → 시·군·구 트리, `is_supported`로 MVP 지역(수성구) 표시 |
| B. 원문 | `source_document` → `document_version` → `provision` | 문서 정체성 / 공포·시행 버전(원문 해시, 확인 상태 4종) / 조·항·호·목·별표 단위 원문 |
| C. 계층 연결 | `delegation` | 상위 조문 → 하위 조문 위임 엣지. 근거 트리의 뼈대 |
| D. 규칙 | `rule`, `rule_condition`, `rule_value`, `rule_evidence` | 기계가 쓰는 기준. 조건(AND) + 값(최대/범위/용도/계산식) + 원문 근거 구간 |
| E. AI·검수 | `extraction_run`, `review_log` | 모델·프롬프트·스키마 버전별 추출 이력, 검수자 승인·수정 기록 |
| F. 필지 | `parcel`, `parcel_designation`, `zone_overlay`, `parcel_building` | 외부 API 캐시(PNU 키), 용도지역·지구·구역, L4 구역 경계 |
| G. 결과 | `review_request`, `review_item`, `explanation` | 기준일·규칙셋 해시로 재현 가능한 검토 결과, 쉬운 설명 캐시 |
| H. 사후 검증 | fact\_ledger, ledger\_fact, ledger\_dismissal, verification\_report, 뷰 displayable\_explanation | 설명의 정답지(사실 원장)와 제외 사유, 시도별 검증 보고서, 화면에 나갈 수 있는 설명만 고르는 뷰 (9장) |

**기능정의서 15장 데이터 구조와의 대응**

| 기능정의서 필드 | 이 스키마 |
| --- | --- |
| 필지정보 `parcel_id, zoning, district, zone` | `parcel.pnu`, `parcel_designation(kind=zoning/district/zone)` |
| 법규정보 `criteria_name, criteria_value, unit` | `rule.title`, `rule_value(num_*, unit)` |
| 법규정보 `legal_basis, article, source, updated_date` | `rule_evidence → provision → document_version(source_url, effective_from, fetched_at)` |
| 법규정보 `applicable_region, applicable_zoning` | `rule.jurisdiction_code`, `rule_condition(field=zoning)` |
| 검토결과 `status, applied_value, result, note` | `review_item(status, result_json, reason_code)` |

**설계 포인트**

- 한 필지의 용도지역은 여러 개일 수 있어(부분 저촉) 필지 테이블에 컬럼 하나로 두지 않고 `parcel_designation`으로 뺐다.
- `rule_evidence.quoted_text`는 `provision.text`의 해당 구간과 정확히 같아야 한다. 이 제약이 AI 환각을 막는 1차 방어선이다.
- `rule.rule_key`(예: `BCR.ZONE.R2G`)는 조례가 개정돼도 유지된다. 새 버전 규칙이 승인되면 이전 규칙은 `superseded`가 되고 `effective_to`가 채워진다.
- `active_rules_at(date)` 함수가 "기준일에 시행 중이고 승인된 규칙"만 돌려준다. 시행일이 NULL인 규칙은 검토에 쓰이지 않는다.

## 6. AI 파싱 파이프라인과 검증 장치

**AI는 오프라인 배치에서 조문을 규칙 JSON으로 바꾸는 일만 하고, 그 출력은 기계 검증 → 사람 검수를 통과해야 DB의 `approved` 규칙이 된다.** 조문을 조·항·호로 쪼개는 일은 AI가 아니라 결정적 파서가 한다.

1. **구조 파싱 (AI 미사용)**: 법령 XML의 조문 태그, 조례 HTML의 "제n조/①/1./가." 패턴으로 `provision` 트리를 만든다. 별표의 표는 `table_json`(행·열)으로 보존한다.
2. **대상 선별**: MVP 6개 카테고리에 해당하는 조문만 고른다. 키워드(건폐율, 용적률, 주차구획, 차로, 건축할 수 있는 건축물 등) + `delegation`으로 연결된 조문.
3. **AI 추출**: 조문 묶음(본문 + 같은 조의 항·호 + 관련 별표 행)을 넣고 `rule_extraction.schema.json` 형식으로만 답하게 한다. 구조화 출력(JSON 모드/도구 호출)으로 형식을 강제한다.
4. **기계 검증** (`앞의 세 가지는 tools/validate_ai_output.py, 범위 검사는 저장 시 상위 규칙을 조회해 수행`):
   - JSON Schema 위반 → `schema_error`
   - `evidence.quote`가 원문에 그대로 없음 → `evidence_error` (서버가 이때 char\_start/char\_end를 계산해 `rule_evidence`에 저장)
   - 값(`num_max` 등)이 그 인용문 안의 숫자가 아님 → `evidence_error`
   - L3 값이 연결된 L1 범위를 벗어남 → `range_error`
5. **사람 검수**: 관리자 화면에서 원문 하이라이트와 추출 규칙을 나란히 보고 승인·수정·반려. 모든 행위는 `review_log`에 남는다. MVP에서는 수성구 대상 규칙 전부를 사람이 승인한다.
6. **재추출 트리거**: 원문 해시 변경, 프롬프트·스키마 버전 변경, 검수자의 `request_reextract`.

**추출 프롬프트 핵심 지시 (요약)**

- 입력에 없는 숫자·용도·법령명을 만들지 말 것. 모르면 `unresolved`에 이유와 함께 남길 것.
- 모든 값에 원문 그대로의 인용(quote)을 붙일 것. 요약·의역 금지.
- 단서·예외("다만, \~의 경우")가 있으면 `exceptions_mentioned`에 인용하고 규칙은 그대로 만들 것. 엔진이 조건부로 처리한다.
- 용도명은 건축법 시행령 별표 1의 용어를 그대로 쓸 것.

**예시로 검증한 결과**: 함께 전달한 예시 출력에서 정상 추출은 통과했고, 숫자를 60→50으로 바꾸거나 원문에 없는 인용을 넣은 출력은 두 오류 모두 잡혀 반려됐다. 예시 조문은 구조 시험용으로 만든 가짜 문구이며 실제 조례 원문이 아니다.

| 실패 유형 | 탐지 방법 | 처리 |
| --- | --- | --- |
| 숫자 환각 | 값이 인용문 숫자 집합에 없음 | 반려, 재추출 |
| 인용 날조 | 인용문 문자열이 원문에 없음 | 반려, 재추출 |
| 조건 누락 (예: 용도지역 빠짐) | 카테고리별 필수 조건 검사 + 사람 검수 | 검수 단계에서 수정 |
| 예외 누락 | "다만" 등 단서 문구가 원문에 있는데 `exceptions_mentioned` 비어 있음 | 경고 표시, 검수 필수 |
| 상위 범위 이탈 | L1 범위와 L3 값 비교 | `range_error`, 데이터 확인 |

## 7. 검토 엔진: 필지 → 적용 규칙 결정

**검토 엔진은 AI 없이 SQL과 코드만으로 동작한다.** 같은 필지·기준일·규칙셋이면 언제나 같은 결과가 나오고, `review_request.ruleset_hash`로 어떤 규칙셋을 썼는지 재현할 수 있다.

**처리 순서**

1. **필지 확정**: 주소 API 결과로 PNU를 만들고 `parcel` 캐시를 확인, 없거나 만료면 지적·토지이용계획 API를 호출한다. 실패한 항목은 null로 두고 `data_notices`에 `PARCEL_PARTIAL`을 넣는다.
2. **지원 지역 확인**: `jurisdiction.is_supported = false`면 필지 정보와 지도만 돌려주고 `REGION_NOT_SUPPORTED` 안내.
3. **입력 키 구성 (L2)**: `{zoning, district, zone, land_category, site_area, jurisdiction_codes}`. 관할 코드는 시·군·구 → 시·도 → 전국 순서의 목록이다.
4. **후보 규칙 조회**: `active_rules_at(as_of_date)` 중 관할 코드가 목록에 있고 `rule_condition`이 입력 키를 모두 만족하는 규칙.
5. **카테고리별 값 결정**: 3장의 값 결정 규칙(L3 우선, L1 범위 확인, L3 없으면 L1 범위로 조건부, 범위 이탈 시 별도 확인)을 적용한다.
6. **L4 중첩**: 필지 경계와 `zone_overlay`를 공간 교차하고, `parcel_designation`의 지구단위계획구역 등 이름도 확인한다. 걸리면 해당 항목을 `MANUAL_CHECK`(`ZONE_OVERLAY`)로 올린다.
7. **참고값 계산**: 대지면적 × 건폐율 = 최대 건축면적 참고값, 대지면적 × 용적률 = 최대 연면적 참고값. 대지면적이 null이면 계산하지 않는다.
8. **근거 트리 생성**: 적용 규칙의 `rule_evidence → provision`에서 출발해 `delegation`을 거꾸로 올라가며 L1 법률까지 노드를 만든다.
9. **별도 확인 항목**: 도로·진출입, 건축선·이격, 높이·일조, 지역 추가 규제는 항상 `manual_checks`로 내보낸다.
10. **시행 예정 개정 안내**: 기준일 이후 시행되는 버전이 있으면 `PENDING_AMENDMENT`로 알린다.

**상태 결정표**

| 상황 | 상태 | reason\_code |
| --- | --- | --- |
| 승인된 L3 값이 있고 L1 범위 안, 예외 없음, 중첩 없음 | 검토 가능 | — |
| L3 값 없음, L1 범위만 있음 | 조건부 검토 | `NO_LOCAL_VALUE` |
| 규칙에 단서·예외 문구가 있음 | 조건부 검토 | `EXCEPTION_CLAUSE` |
| 용도 입력이 있어야 계산 가능 (주차대수) | 조건부 검토 | `NEEDS_USE_INPUT` |
| L3 값이 L1 범위를 벗어남 | 별도 확인 필요 | `OUT_OF_RANGE` |
| L4 특화구역과 겹침 | 별도 확인 필요 | `ZONE_OVERLAY` |
| 용도지역 등 필수 입력이 null | 별도 확인 필요 | `DATA_MISSING` |
| 해당 카테고리 승인 규칙 없음 | 별도 확인 필요 | `DATA_MISSING` + `RULE_NOT_APPROVED` 안내 |

**용도(ZONING\_USE) 처리**: 국토계획법 시행령의 용도지역별 "건축할 수 있는 건축물" 별표와 조례 위임분을 `rule_value(enum_allowed / enum_conditional / enum_prohibited)`로 저장하고, 화면 묶음(주거·근린생활·업무·기타)으로 모아 각 묶음의 가장 보수적인 상태를 대표 상태로 쓴다.

## 8. 쉬운 설명 생성과 필터링

**쉬운 설명 AI는 검토 엔진이 이미 확정한 `review_item` 하나만 입력으로 받아 문장으로 바꾼다.** 법규를 다시 읽거나 판단하지 않으므로, 설명이 틀려도 숫자·상태·근거는 바뀌지 않는다.

**흐름**

1. 검토가 끝나면 항목마다 캐시 키 `sha256(카테고리 | 규칙 id들 | 원장 해시 | 상태 | 독자 | 프롬프트 버전)`를 만든다. 원장 해시가 들어가므로 원문이 바뀌면 캐시도 자동으로 무효가 된다.
2. `explanation`에 같은 키가 있으면 재사용한다. 같은 용도지역의 수성구 필지들은 대지면적 외에 입력이 같아 대부분 캐시로 처리된다.
3. 없으면 AI를 호출해 `explanation.schema.json` 형식으로 받는다.
4. 사후 검증기(9장)로 사실 원장과 대조한다: 날조, 세부 왜곡(값·단위·비교어·성격), 누락, 상태 과장.
5. 통과(PASS)하면 저장 후 `review_item.explanation`에 붙인다. 실패하면 반려 사유를 넣어 최대 2회 재생성하고, 그래도 실패하면 원문 인용 템플릿 설명을 같은 검증에 다시 통과시켜 쓴다. 템플릿마저 실패하면 쉬운 설명 없이 근거 원문만 보여준다.

**독자별 두 가지 버전**

| 독자 | 문체 | 예시 headline (건폐율) |
| --- | --- | --- |
| `owner` 토지소유주 | 용어를 풀어 쓰고 "\~할 수 있어요" | 땅의 60%까지 건물을 앉힐 수 있어요 |
| `architect` 설계 실무자 | 용어 유지, 수치와 근거 위주로 짧게 | 건폐율 60% 이하 (시 도시계획 조례) |

**설명 프롬프트에서 금지하는 것**

- 입력에 없는 숫자, 법령명, 조문 번호
- "가능합니다", "허가됩니다" 같은 단정 (상태가 검토 가능이어도 "검토할 수 있어요"로 표현)
- 상태보다 낙관적인 표현 (조건부 항목을 검토 가능처럼 쓰는 것)

위 예시의 60%는 기능정의서의 화면 예시값이며 실제 수성구 필지에 적용된 값이 아니다.

## 9. 사후 검증기: 화면 직전 환각 차단

**AI가 쓴 설명은 사후 검증기를 통과(PASS)해야만 화면에 나간다.** 검증기는 설명을 '사실 원장'과 문장 단위로 대조해 날조, 세부 왜곡, 누락을 모두 환각으로 보고 반려한다. 세 번 모두 통과하지 못하면 원문 인용으로 만든 템플릿 설명을 보여 주며, 검증되지 않은 문장은 어떤 경우에도 화면에 나가지 않는다.

**환각의 정의와 탐지 방식**

| 유형 | 예 | 탐지 방법 | 오류 코드 |
| --- | --- | --- | --- |
| 날조: 없는 숫자·금액·날짜 | "위반 시 과태료 50만원" | 문장의 모든 수치를 파싱해 원장 값과 대조 | `FABRICATED_VALUE` |
| 날조: 없는 법령·조문·용도지역 | "주차장법 제19조에 따라" | 법령명·조문·용도지역 명칭을 원장 목록과 대조 | `REFERENCE_FABRICATED`, `LAW_NAME_FABRICATED`, `SUBJECT_MISMATCH` |
| 날조: 근거 없는 문장 | "요즘 많이들 이렇게 지어요" | 모든 문장은 원장 fact\_id를 인용해야 함 + 의미 검증 | `UNGROUNDED_SENTENCE`, `SEMANTIC_NOT_IN_SOURCE` |
| 세부 왜곡: 값 | 1년 → 8개월, 1년 → 365일 | 기간을 개월·일로 정규화해 비교 (1년 = 12개월만 같은 값으로 인정) | `DETAIL_MISMATCH` |
| 세부 왜곡: 비교어 | 2.5m 이상 → 2.5m 초과, "이하" 생략 | 숫자 바로 뒤의 이하·미만·이상·초과·이내를 추출해 비교 | `COMPARATOR_MISMATCH`, `COMPARATOR_MISSING` |
| 세부 왜곡: 단위 | 2.5m → 250cm, ㎡ → 평 | 단위 환산을 허용하지 않음. 환산하면 같은 값이면 단위 오류로 표시 | `UNIT_MISMATCH` |
| 세부 왜곡: 서술 성격 | "설치하여야 한다" → "설치하지 않아도 돼요" | 의무·금지·허용·면제 표현을 분류해 원문과 비교 | `POLARITY_MISMATCH` |
| 누락: 사실 전체 | 단서(예외) 조항이 빠짐 | 반드시 설명할 사실(must\_mention)을 인용한 문장이 없음 | `OMISSION` |
| 누락: 세부 | 예외를 언급했지만 "적용되지 않는다"는 뜻이 빠짐, "사용승인일부터"가 빠짐 | 인용 문장에 값·비교어·핵심어·성격이 모두 있는지 | `OMISSION_DETAIL` |
| 누락: 원장 자체 | 원문에 있는 기간을 원장에 넣지 않음 | 원문에서 뽑은 후보 전체와 원장 대조 | `LEDGER_INCOMPLETE` |
| 상태 과장 | 조건부 항목에 "허가를 받을 수 있어요" | 단정 표현 사전 + 유의 문장 필수 | `OVERSTATEMENT`, `CAUTION_MISSING` |

**사실 원장 (검증의 정답지)**

- 규칙이 근거로 삼는 원문 조문에서 결정적 추출기가 숫자·기간·날짜·비교어·조문 참조·단서("다만")·의무/금지 문장·용도지역 명칭을 후보로 **전부** 뽑는다.
- 검수자는 각 후보를 원장 사실로 올리거나, 사유를 적어 제외한다. 사유 없는 제외는 불가하고, 처리되지 않은 후보가 하나라도 남으면 원장을 승인할 수 없다(DB 제약). **원문 누락은 여기서 먼저 막힌다.**
- 사실마다 정규화 값(1년 → 12개월, 이내 → 이하), 서술 성격, 핵심어(동의어 허용), 필수 여부를 둔다.
- 엔진이 계산한 값(대지면적, 참고값, 검토 상태)도 엔진 출처 사실로 넣어 설명에서 인용할 수 있게 한다.
- 원장 검수는 6장의 규칙 검수와 같은 화면에서 함께 한다.

**검증 순서**

1. 형식·근거 연결: 스키마, 모든 문장의 fact\_id 인용, 없는 fact\_id 거부
2. 수치·기간·단위·비교어 대조 (원문과 설명에 같은 한국어 파서를 적용)
3. 명칭 대조: 법령명, 조문, 용도지역
4. 서술 성격 대조: 의무·금지·허용·면제
5. 누락 검사: 필수 사실 커버리지
6. 상태 과장 검사
7. 원장 완전성 재확인
8. 의미 검증: 작성 모델과 분리된 판정 모델이 원장 인용문만 보고 문장별 함의(ENTAILED / CONTRADICTED / NOT\_IN\_SOURCE)와 사실별 커버리지(COVERED / PARTIAL / MISSING)를 판정

1–7은 AI 없이 동작하는 결정적 검사다. 8은 숫자로 잡히지 않는 의미 왜곡을 잡기 위한 단계로, 실패를 추가할 수만 있고 1–7의 실패를 지울 수 없다. 판정 모델이 시간 초과되거나 형식을 어기면 통과가 아니라 실패(`JUDGE_UNAVAILABLE`)로 처리한다.

&#91;embedded content: 사후 검증 흐름 · 생성 3회, 실패 시 원문 템플릿, 최후에는 근거 원문만\]

화면으로 가는 길은 두 개뿐이다: 검증을 통과한 AI 설명, 또는 검증을 통과한 원문 템플릿. 둘 다 실패하면 설명 없이 근거 원문만 보인다.

**화면 노출 규칙**

| 검증 결과 | 화면에 보이는 것 | 표시 |
| --- | --- | --- |
| 첫 생성 또는 재생성(최대 2회)에서 PASS | AI 쉬운 설명 | "원문 대조 검증 완료", 문장마다 근거 원문 보기 |
| 세 번 모두 FAIL | 원장 인용문으로 만든 템플릿 설명 (같은 검사 1–7을 통과해야 함) | "원문 그대로 표시" 안내 |
| 템플릿도 FAIL (원장 오류) | 쉬운 설명 없이 근거 원문만 | 관리자 알림 |

DB도 이 규칙을 강제한다. `explanation`은 PASS 보고서 없이 화면용으로 표시할 수 없고(CHECK 제약), 화면 API는 원장 해시가 일치하는 PASS 설명만 담은 `displayable_explanation` 뷰만 읽는다. 조례 개정으로 원장이 바뀌면 이전 검증은 자동으로 무효가 된다.

**시험 결과**: 1년 기간, 연면적 조건, 너비 기준, 단서, 설치 의무를 담은 예시 조문(구조 시험용 가짜 문구)으로 37개 시나리오를 돌렸다. 1년→8개월, 1년→1년 6개월, 1년→365일, 이상→초과, 비교어 생략, 2.5m→250cm, 의무→면제, 용도지역 변경, 과태료·날짜·조문 날조, 예외 누락, 조건 누락, 핵심어 누락, 단정 표현이 모두 반려됐다. 1년↔12개월, m↔미터처럼 뜻이 같은 표기는 통과했고, 재생성 루프와 템플릿 대체 경로도 동작을 확인했다.

**한계**: 결정적 검사는 숫자·명칭·정해진 표현만 확실하게 잡는다. "지하에만 설치할 수 있다"처럼 숫자 없는 날조는 서술 성격 대조와 의미 검증에 기댄다. MVP 기간에는 PASS 설명도 수성구 검증 20건 전부를 사람이 다시 읽고, 판정 모델이 놓친 사례를 시험 케이스로 추가한다.

## 10. 웹 API 명세 요약

**웹이 쓰는 공개 API는 4개이고, 화면 3개(초기·검토 중·결과)에 하나씩 대응한다.** 응답 본문 형식은 `review_result.schema.json`이 정의한다.

| 메서드·경로 | 화면 | 요청 | 응답 |
| --- | --- | --- | --- |
| `GET /v1/address/search?q=` | 초기 화면 | 도로명·지번 주소 문자열 | 후보 목록: 도로명, 지번, PNU, 좌표, `supported` 여부 |
| `GET /v1/parcels/{pnu}` | 결과 상단·지도 | PNU | 대지면적, 지목, 용도지역·지구·구역, GeoJSON 경계, 항목별 출처·조회시각 |
| `POST /v1/reviews` | 검토 중 | `{pnu, as_of_date?, audience: "owner"/"architect"}` | `202 {review_id}` |
| `GET /v1/reviews/{id}` | 검토 중 → 결과 | — | 진행 중이면 단계별 진행상태(대지정보 조회 ✓, 용도지역 확인 ✓, 건축 법규 검토 …), 완료면 `review_result` 전체 |

**쉬운 설명 필드**: 각 항목의 `explanation`은 `{display_source, content, verification}`이다. `display_source`는 `ai_verified`(검증 통과 AI 설명), `template_fallback`(원문 인용 템플릿), `basis_only`(설명 없이 근거만) 중 하나이고, `verification`에는 검증 결과(PASS), 보고서 id, 검증 시각, 필수 사실 커버 수(예: 6/6)가 들어간다. 웹은 `basis_only`가 아닐 때만 설명을 그리며, "원문 대조 검증 완료" 표시와 문장별 근거 원문 보기를 함께 제공한다. 검증 보고서 원문은 관리자 API `GET /admin/verifications/{report_id}`로 본다.

**보조 API**

- `GET /v1/rules/{rule_id}/basis` : 근거 상세보기. 근거 트리 + 원문 조문 전체 + 국가법령정보센터 링크
- `GET /v1/regions` : 지원 지역 목록 (초기 화면의 "현재 MVP는 대구 수성구" 문구용)

**관리자 API (검수 화면용, 인증 필수)**

- `GET /admin/extractions?status=` : 검수 대기 추출 결과
- `POST /admin/rules/{id}/approve | reject | edit` : 검수 처리, `review_log` 기록
- `POST /admin/documents/{id}/refetch` : 원문 재수집
- `POST /admin/zones` : L4 특화구역 수동 등록 (고시번호, 일자, 경계 또는 PNU 목록)

**오류 응답** (기능정의서 14장 문구와 연결)

| 코드 | 상황 | 화면 문구 |
| --- | --- | --- |
| `ADDRESS_NOT_FOUND` (404) | 주소 검색 결과 없음 | 주소를 찾을 수 없습니다. 도로명 또는 지번주소를 다시 확인해주세요. |
| `PARCEL_PARTIAL` (200 + notice) | 일부 필지 정보 조회 실패 | 해당 토지의 일부 정보를 불러오지 못했습니다. |
| `REGION_NOT_SUPPORTED` (200 + notice) | 법규 데이터 미등록 지역 | 현재 해당 지역의 법규 검토 데이터가 준비되지 않았습니다. |
| `UPSTREAM_UNAVAILABLE` (503) | 외부 API 장애 | 공공데이터 조회가 지연되고 있습니다. 잠시 후 다시 시도해주세요. |

외부 API 키는 서버에만 두고, 지도 타일용 키만 도메인 제한을 걸어 브라우저에서 쓴다.

## 11. MVP 구현 순서와 리스크

**데이터가 먼저다: 수성구 필지 10개의 결과가 손으로 검토한 값과 일치할 때까지 화면 작업보다 규칙 DB를 우선한다.** 순서는 사업계획서 일정(11월 데이터·법규, 12월 기능 연결, 1월 검증)에 맞췄다.

1. **스키마·수집기**: `schema.sql` 적용, 국가법령정보 Open API 키 발급, 대상 문서 등록 — 국토계획법·시행령, 건축법·시행령(별표 1), 주차장법·시행령·시행규칙, 대구광역시 도시계획 조례, 대구광역시 건축 조례, 수성구 주차장 관련 조례.
2. **구조 파서**: 법령 XML·조례 HTML → `provision`. 별표 표 파싱 포함.
3. **AI 추출 + 검수 화면**: 6개 카테고리 규칙 추출, 검증기 연결, 관리자 승인 화면. 수성구 규칙 전부 사람이 승인.
4. **필지 연동**: 주소 API → PNU → 지적·토지이용계획 조회, 캐시.
5. **검토 엔진**: 값 결정·상태 결정·근거 트리·별도 확인 항목.
6. **쉬운 설명**: 설명 프롬프트, 사실 원장 추출·검수, 사후 검증기와 의미 검증 모델, 캐시. 결정적 검사를 먼저 붙이고, 판정 모델은 수성구 20건에서 놓침을 확인하며 조정한다.
7. **웹 연결**: 공개 API 4개로 초기·검토 중·결과 화면 구현, 지도 표시.
8. **검증**: 수성구 실제 필지 10개 × 조건 2개 = 20건을 실무자 수작업 결과와 대조, 불일치는 규칙 수정 후 재검토.

**리스크와 대응**

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 조례 별표가 이미지·복잡한 표로 제공됨 | 파싱 실패, 값 누락 | 별표는 MVP에서 수작업 입력 허용(`created_by=human`), 근거로 원문 링크 |
| AI가 단서·예외를 놓침 | 잘못된 "검토 가능" | 단서 문구 탐지 경고 + 사람 검수 필수, 예외 있으면 조건부 |
| 토지이용계획 API 응답의 용도지역 명칭이 규칙 조건과 다름 | 규칙 매칭 실패 | 명칭 정규화 사전(`UQA122` 같은 코드 ↔ 법정 명칭)을 별도 테이블로 운영 |
| 개정 직후 원문은 바뀌었는데 규칙은 이전 값 | 오래된 기준 표시 | 해시 변경 시 해당 문서 규칙을 자동 `needs_review`, 결과에 개정 안내 |
| 지구단위계획 내용을 자동 반영하지 못함 | 실제 기준과 차이 | 중첩 시 무조건 별도 확인으로 격상, 고시 링크 제공 |
| 공공 API 호출 한도·장애 | 조회 실패 | 30일 캐시, 실패 항목만 null 처리하고 나머지 결과 제공 |
| AI 설명의 숫자 없는 날조·의미 왜곡 | 원문과 다른 설명 노출 | 서술 성격 대조 + 분리된 판정 모델, 판정 실패 시 통과 불가, MVP 기간 PASS 설명 전수 사람 재확인 (9장) |

**함께 전달한 파일**: `schema.sql`(DB DDL), `schemas/`(규칙 추출·검토 결과·쉬운 설명·사실 원장·검증 보고서·판정 결과 JSON 스키마), `tools/`(AI 출력 검증기, 한국어 수치 파서, 사실 원장 추출기, 사후 검증기와 37개 환각 시나리오 테스트), `prompts/`(쉬운 설명 작성·의미 검증 프롬프트), `examples/`(구조 시험용 예시 — 실제 법규 값 아님).
